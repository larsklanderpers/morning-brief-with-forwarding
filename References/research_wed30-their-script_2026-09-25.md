# Research Note -- Third-party code on the merchant's own pages (Brevo, Ribon, TanStack/CrowdSec, script controls)

For: Wed 30 Their Script, Your Storefront · Depth: deep · Date: 2026-09-25

## Bottom line

The thesis holds cleanly for Brevo and wobbles for Ribon. Brevo's own write-up confirms an attacker served a ClickFix page through Brevo's forms script, chat widget and SDK loader into customer sites for about four and a half hours on 14 Sep 2026, and four days earlier a separate Brevo flaw let an attacker send phishing from real customers' accounts (Trezor, CoinTracking), which is the "under the merchant's name" point in its purest form. Ribon is weaker than the seed implies: BigCommerce's merchant email says scripts were injected, but the only merchant on record (Master of Malt) says the stolen app key was used to pull stored customer records, so the shopper may never have "met" anything on screen; the cleaner BigCommerce precedent is ZAGG/FreshClicks (2024), a card skimmer at checkout. The honest limit: PCI DSS 6.4.3 and 11.6.1 cover payment pages only, and neither SRI nor a domain allowlist CSP would reliably have stopped Brevo, because the bad code came from the vendor's own trusted, unversioned URLs.

## What's solid

- Brevo incident window, 14 Sep 2026 (UTC): attacker created a hostname on a Brevo-owned domain 14:23; malicious Cloudflare Worker live on brevo.com from 15:01; routed to sibforms.com and three embedded JS files at 16:07; Brevo security opened investigation 19:33; Worker removed 20:30. -- Brevo status write-up, primary, https://status.brevo.com/incidents/01M2QBC4EZ24ZACW6SWQYVW8N3/write-up ; matches BleepingComputer and SecurityWeek.
- Components hit: Brevo forms script, Brevo Conversations widget, Brevo SDK loader, plus brevo.com, sendinblue.com, login/account/my/onboarding.brevo.com, sibforms.com. Not affected per Brevo: app.brevo.com, API, email systems, account data. -- Brevo write-up, primary (above). Byteiota names the files as sdk-loader.js, brevo-conversations.js and the forms script (secondary only).
- Root cause: "a long-lived Cloudflare API key with full account permissions was stored in application source code." Brevo says the key was "first misused in late August 2026." -- Brevo write-up, primary; SecurityWeek quotes the same.
- Origin untouched: the Worker rewrote responses at the CDN edge and stripped security headers such as Content-Security-Policy; "our origin servers and files remained unmodified." -- Brevo write-up, primary; BleepingComputer.
- What ClickFix asked: a fake "Cloudflare, verify you are human" page told visitors to press Win+R, Ctrl+V, Enter, running a clipboard command that downloaded malware to Windows machines. Shown selectively: "most visitors and repeat visits saw nothing." On WordPress sites with a logged-in admin, it silently tried to install a malicious plugin ("Web Media Optimizer" per BleepingComputer). -- Brevo write-up, primary; BleepingComputer.
- Brevo remediation: keys revoked, HashiCorp Vault with rotation, alerting on Cloudflare Worker/route/DNS audit events, "integrity protection for versioned embedded assets where technically possible," external scanning of its public scripts. -- Brevo write-up, primary.
- Separate, earlier Brevo incident, 10 Sep 2026: SAML SSO scoping flaw. Attacker created a Brevo account, enabled SSO, invited legitimate users, and got access to every organization those users could reach. 138 accounts accessed; 43 had contacts exported; 6 used to send phishing. Brevo: "Customers trust us with access to their audiences, and in this case we failed to protect it." -- Brevo status write-up, primary, https://status.brevo.com/incidents/01M266V1CZKJQNGZRNEGFD5CQE/write-up ; Malwarebytes names Trezor, CoinTracking, BitBox as affected senders and quotes the lures ("Critical Security Alert: STM32 Entropy Bug Identified" asking for wallet backup), https://www.malwarebytes.com/blog/news/2026/09/crypto-customers-targeted-by-scammers-after-email-marketing-provider-breach . Brevo's write-up does not link the two incidents.
- BigCommerce (now branded "Commerce") public notice, 17 Sep 2026: API credentials of developer "Be A Part Of," a Fastr company, "had been compromised as a result of a Fastr system compromise. This was not a breach of Commerce systems or the BigCommerce platform. The only way to be affected ... is for the merchant to have independently installed a Fastr developed application. Commerce has limited visibility into whether the actions taken by the application are valid or the result of the malicious actor." Merchants told to contact Fastr. -- Commerce Trust Center, primary, https://security.bigcommerce.com/ . Note: the public notice does not mention scripts or data types.
- BigCommerce merchant email (as quoted by press): Ribon and Ribon 1.5 credentials "had been compromised and used to inject malicious scripts into a small number of merchant storefronts"; apps uninstalled; logs shared with the developer. -- BleepingComputer (21 Sep) and SecurityWeek, two secondaries quoting the same text; primary email not seen.
- Ribon window and data: access 13 Sep 17:21 BST to 17 Sep 21:12 BST; names, emails, phone numbers, shipping addresses; no passwords or card data. Master of Malt notified customers 18 Sep; ICO reference IC-569770-Y1R9 on 19 Sep. -- Cyberpress/GBHackers paraphrasing Master of Malt, plus BleepingComputer, SecurityWeek, TechRadar on data types. Master of Malt's own notice not reached.
- TanStack: CVE-2026-45321, CNA GitHub, CVSS 3.1 9.6 Critical, CWE-506. 84 malicious versions of 42 @tanstack/* packages published 11 May 2026 19:20 to 19:26 UTC via pull_request_target misconfiguration, Actions cache poisoning across the fork boundary, and OIDC token extraction from runner memory. Credential stealer (AWS, GCP, Kubernetes, npm, GitHub, SSH). -- NVD, primary, https://nvd.nist.gov/vuln/detail/CVE-2026-45321 ; GHSA-g7cv-rxg3-hmpx, primary, https://github.com/TanStack/router/security/advisories/GHSA-g7cv-rxg3-hmpx . NVD lists a CISA KEV reference.
- TanStack detection: external researcher (StepSecurity) disclosed at 19:46 UTC, about 26 minutes after first publish; "No internal monitoring existed"; download count still an open question. -- TanStack postmortem, primary, https://tanstack.com/blog/npm-supply-chain-compromise-postmortem
- CrowdSec (one clause only): ~170 private repos copied 22 May 2026 with a token stolen via the TanStack malware; code surfaced on a forum 16 Sep; 83 user emails and 51 prospective investors (2020) exposed; CrowdSec says no production or customer data. -- CrowdSec blog 18 Sep, primary, https://www.crowdsec.net/blog/tanstack-supply-chain-attack-analysis ; The Hacker News 19 Sep.
- PCI DSS 6.4.3 and 11.6.1 became effective 31 March 2025 (future-dated in v4.0, now v4.0.1). Purpose per PCI SSC: "ensuring that payment page scripts are properly authorized, checked for integrity, and monitored for tampering," and managing "security-impacting HTTP headers." -- PCI SSC blog, primary, https://blog.pcisecuritystandards.org/important-updates-announced-for-merchants-validating-to-self-assessment-questionnaire-a (30 Jan 2025) and https://blog.pcisecuritystandards.org/new-information-supplement-payment-page-security-and-preventing-e-skimming (10 Mar 2025).
- Requirement text. 6.4.3: all payment page scripts loaded and executed in the consumer's browser are managed so that each is authorized, integrity is assured, and an inventory is kept "with written justification as to why each is necessary." 11.6.1: a change- and tamper-detection mechanism alerts on unauthorized modification to "the security impacting HTTP headers and the script contents of payment pages as received by the consumer browser," run "at least once every seven days OR periodically" per a targeted risk analysis. -- Adyen docs and Foregenix, two secondaries agreeing on wording; PCI SSC standard PDF itself not reached (see Couldn't verify).
- SAQ A carve-out: effective 31 March 2025, PCI SSC removed 6.4.3, 11.6.1 and 12.3.1 from SAQ A and replaced them with an eligibility criterion that the merchant "has confirmed that their site is not susceptible to attacks from scripts that could affect the merchant's e-commerce system(s)." -- PCI SSC blog, primary (30 Jan 2025).
- SRI mechanics: browser hashes the fetched file and "will refuse to load the resource" on mismatch; cross-origin use requires CORS. -- MDN, primary reference, https://developer.mozilla.org/en-US/docs/Web/Security/Subresource_Integrity
- Brevo's documented tracker snippet is `<script src="https://cdn.brevo.com/js/sdk-loader.js" async>` with no integrity attribute, unversioned, and it loads further code dynamically. -- Brevo developer docs, primary, https://developers.brevo.com/docs/getting-started-with-js-implementation
- Precedent, merchant liable for vendor script: ICO fined Ticketmaster UK GBP 1.25m (13 Nov 2020) over a third-party Inbenta chatbot on its payment page; ~9.4m EEA customers potentially affected; ICO said third-party JavaScript on pages processing personal data is "a known security risk." -- Hunton and other law-firm write-ups (two secondaries); ICO page 404 at fetch time.
- Precedent, script on payment page: ICO fined British Airways GBP 20m (reduced from GBP 183.39m); attacker modified JavaScript to send card data to "BAways.com"; ~429,612 people; skimming live 21 Aug to 5 Sep 2018; ICO listed hardcoded credentials and lack of file integrity monitoring among failings. -- ICO penalty notice, primary, https://ico.org.uk/media2/migrated/2618421/ba-penalty-20201016.pdf
- Precedent, BigCommerce app skimmer: ZAGG, 26 Oct to 7 Nov 2024, compromised FreshClicks app injected card-scraping code at checkout; BigCommerce uninstalled the app. -- BleepingComputer and Security Affairs (two secondaries; BigCommerce quote carried in BleepingComputer).
- Shopify removed checkout.liquid and "additional scripts" from Thank you/Order status pages on 28 Aug 2025 (Plus) and 26 Aug 2026 (non-Plus); info/shipping/payment pages already unsupported. -- Shopify dev docs, primary, https://shopify.dev/docs/storefronts/themes/architecture/layouts/checkout-liquid

## What's contested / watch out

- Ribon mechanism. BigCommerce says "inject malicious scripts into ... storefronts." Master of Malt says the key was used "to gain access to customer data," and BleepingComputer's own analysis says the Ribon attackers "used a compromised application key to access existing customer records through BigCommerce," unlike ZAGG where card data was captured at checkout. So it is not established that any shopper saw or ran attacker code. Safe line: "an app the merchant installed held a key to the merchant's store, and the attacker used it." Do not write "Ribon put an attacker's script on shoppers' screens" as fact.
- Ribon scale: BigCommerce says "a small number of merchant storefronts"; Master of Malt/TechRadar say Ribon was installed on "hundreds" of stores. Installed base is not the victim count. No number from Fastr, which had not commented publicly at press time.
- Brevo "100,000+ websites": Cybernews attributes it to PublicWWW scans finding ~117,000 pages referencing Brevo infrastructure. That is reach, not victims. ClickFix was shown selectively. Say "up to roughly 100,000 sites loaded the affected scripts, per Sansec," not "100,000 sites infected."
- Brevo duration: "about 5 and a half hours" (Brevo, brevo.com 15:01 to 20:30) versus customer-site exposure 16:07 to 20:30, about 4 hours 23 minutes; SecurityWeek cites Sansec at "~4 hours." For a storefront piece, use "about four and a half hours on customer sites."
- Detection: Brevo opened its investigation at 19:33, about 3.5 hours into customer-site impact; BleepingComputer credits Sansec with discovering and reporting it. Brevo's write-up does not credit Sansec in what was extracted; do not assert who told whom without Sansec's page (unreached).
- "SRI would have stopped it in ten minutes" (Byteiota) is too easy. SRI needs a fixed file; Brevo's loader is unversioned and pulls more code at runtime, and Brevo itself now promises integrity only "for versioned embedded assets where technically possible." A merchant pinning a hash would have broken the widget on every Brevo update.
- CSP: the Worker stripped CSP on Brevo's own responses, not on merchant pages. A merchant CSP allowlisting Brevo domains would still have allowed the malicious code, since it came from Brevo URLs and a hostname on a Brevo-owned domain (cdn.sendibt1.com per Cybernews; "Brevo-owned domain" per Brevo). A strict connect-src might have blocked a callout to a truly foreign domain; not established. Treat CSP value here as inference.
- PCI scope counter-take: 6.4.3 and 11.6.1 apply to payment pages only. Brevo's forms/chat typically sit on marketing and account pages; ClickFix aimed at the visitor's PC, not card data; Ribon took contact data. PCI would likely not have been triggered by either. And SAQ A merchants (fully outsourced iframe or redirect) now self-attest rather than implement. TrustedSec calls the new criterion vague enough that merchants may learn they were ineligible "during assessments or breach investigations." -- https://trustedsec.com/blog/the-hidden-trap-in-the-pci-dss-saq-a-changes (practitioner view).
- Skeptic's strongest shot at the thesis: the part that failed at Brevo was not "someone else's code" but someone else's credential and CDN configuration; the JS files were fine at origin. The factory metaphor should include config and keys, not just packages.
- "The customer met it under the merchant's name": true in look and feel for Brevo (visitor sees the merchant's URL). For Ribon the customer "meets" it only in the breach letter and any follow-on phishing.

## The economics

- Breach cost: IBM 2026 global average $4.99M, up 12%, record. -- IBM, primary, https://www.ibm.com/reports/data-breach . US average $11.5M. -- HIPAA Journal, secondary. Supply chain compromise +$227,250 per breach and 258 days to identify and contain. -- Reflectiz (vendor) and HIPAA Journal; label as "IBM figures as reported," not verified at IBM.
- Third-party share: Verizon 2026 DBIR (19 May 2026): "third-party involvement in breaches is up 60%." -- Verizon news release, primary, https://www.verizon.com/about/news/breach-industry-wide-dbir-finds
- Regulatory cost of someone else's script on your page: BA GBP 20m (primary); Ticketmaster GBP 1.25m (secondaries). In both, the regulator held the site owner responsible.
- Cost to merchants in the current cases: not disclosed by anyone. Visible costs so far are notification, ICO reporting (Master of Malt), WordPress cleanup (Brevo customers), and class-action solicitation (Emery Reddy has a Ribon page). ZAGG offered 12 months of Experian monitoring (Security Affairs).
- Cost of script controls: Cloudflare offers basic script monitoring on all plans including Free; malicious-script detection, code-change detection and alerts need the paid "Client-Side Security Advanced" tier. -- Cloudflare docs, primary, https://developers.cloudflare.com/page-shield/ . SRI and CSP are free in license terms; the cost is engineering time and breakage when a vendor updates an unversioned script. No neutral figure found for commercial client-side monitoring pricing.
- Irony worth noting: at Brevo the attack ran on Cloudflare Workers, the same edge layer vendors sell for script protection. The control plane is itself a third-party part.

## Angles this opens

- The part that broke was a key, not a package: Brevo (hardcoded Cloudflare key), Ribon (app API key), TanStack (OIDC token from runner memory). The "factory" is parts plus the credentials that let parts change themselves.
- The unversioned loader problem: vendors ship `latest` by design so they can patch you; that same property makes integrity pinning impossible. Ask vendors for versioned, hash-published builds. Brevo is now moving that way "where technically possible."
- The liability asymmetry: platform notice says it has "limited visibility"; regulators (BA, Ticketmaster) put the bill on the site owner. The merchant owns the outcome of code it cannot see.
- PCI drew the line at the payment page; attackers moved to the rest of the page (forms, chat, ClickFix on the visitor's PC). Contact-data theft (Ribon) sits outside card rules but inside GDPR/state breach laws.
- Shopify's answer: take arbitrary scripts off checkout entirely (non-Plus cutoff 26 Aug 2026). Is platform lockdown the only control that scales for small merchants?
- A practical merchant checklist the piece can defend: inventory every third-party tag by page; strip vendor tags from checkout and account pages; prefer vendors offering versioned files with published hashes; CSP with report-uri to at least see changes; weekly DOM/header change detection (the 11.6.1 bar) even off the payment page; scope app API permissions (read customers only if needed) and review installed apps quarterly.
