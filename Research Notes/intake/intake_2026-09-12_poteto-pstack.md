## Extracted

### Part 1: "Verification is all you need" (posted 31 Aug 2026, 16:09 UTC; 5,734 likes, 513 reposts)

- **Framing.** Tan says volume matters once quality holds, and credits pstack with letting them keep
  the Grok Bot codebase clean as the team (engineers and non-engineers) grew and landed hundreds of
  PRs a day. They describe themselves as the codebase's gardener and maintainer.
- **Verification as critical infrastructure.** An agent that can check its own work can loop until
  it succeeds without a human as the bottleneck. They treat the verification skill as infrastructure,
  not "just" a skill, and suggests an on-call rotation for it.
- **Setup.** Install pstack, run `/create-verification-skill`, and add Dr Eggbot (ships with pstack;
  builds coding bots and, they say, non-coding bots "with the same rigor"). A daily routine runs
  `/maintain-verification-skill`.
- **Tech stack matters.** Rich runtimes (Chrome DevTools Protocol, iOS simulator, perf traces) make
  agent verification easy; if the stack lacks them, build your own debugging tools or pick a
  different stack.
- **"Build the Lever."** pstack's principle: give agents tools rather than just markdown. For
  verification that means a small CLI that scripts the app (`/control-app start`, `navigate`,
  `screenshot`, `perf-trace`, `login`, `api-call`). Fewer tokens, more reproducible, testable.
  Their agent-friendly CLI properties: composable (Ousterhout's deep modules), `--dry-run` on anything
  destructive, subcommands for gradual disclosure, error messages that say what to do instead, rich
  `--help`, machine-readable (JSON) output.
- **Parallelism.** Recommends Cursor cloud agents over worktrees (worktrees cost disk and cap out
  around ten agents on one machine). Cloud agents get a real computer; the environment is snapshotted
  after first build.
- **Feature Map.** A searchable markdown map of every feature, what it does and how a user reaches
  it, living inside the verification skill (`references/features/` with a README index). Generated by
  the create skill. They call it "materialized memory" and argues the codebase is the ultimate memory;
  the map is a compact, token-saving projection of it. Maintain daily.
- **Usage patterns.** `/poteto-mode build ... use /control-app to verify ... show me a video and
  screenshots as proof`. In Grok Bot they have the bot spawn a cloud agent so the bot stays a
  coordinator with a clean context. `/swarm` fans out many cloud agents to confirm a perf win at
  sample size or to fuzz for regressions. Routines or Cursor Automations can watch a Slack feedback
  channel and try to reproduce every report, even auto-fix.
- **Top comment** (@maria_rcks): how do feature maps avoid going stale or bloated? Tan's reply in the
  thread (9 Sep) is only a link, which resolves to Part 2; it does not answer the question. The
  example repo below does.

### Part 2: "The art of supervising someone smarter than you" (posted 9 Sep 2026, 17:02 UTC; about 300K views, 2,815 likes)

- **Two failure modes** they see in frontier models: under-specified intent, and too little context
  to do the work correctly. Both come down to priming the context window.
- **Indirect prompt.** Ask the agent to read a Slack thread and restate the problem in its own words
  before acting: compresses noise, surfaces misunderstandings early, avoids leading it with your own
  hypotheses.
- **`/teach`, `/how`, `/why`.** `/how` traces runtime mechanics, spawning parallel explorers on fast
  models for big subsystems. `/why` pulls historical intent in parallel from git history, PR review
  comments, Linear, Notion, Slack, Datadog, Sentry, code lineage and analytics. `/teach` makes the
  agent explain its choice and trade-offs; they find this also stops agents stating things
  confidently without reading the code.
- **`/recall`.** Pulls recent context from past chat transcripts so a fresh agent starts warm.
- **README-driven development.** Plan by writing the tutorial or README first and working backwards.
  Tan's first agent-written README mixed tutorial, how-to, explanation and reference in one document,
  so they built `/technical-writing`, which separates the four Diataxis modes, and `/unslop`.
- **Prototyping playbook.** Named mistakes: accepting the agent's first design, and overcooking a
  plan without evidence. The playbook builds two or three variants, drives each with the verification
  CLI, and measures. "Prototyping is planning, but with code." pstack ships 23 playbooks as of 0.15.0,
  loaded conditionally inside `/poteto-mode`.
- **`/architect`.** Ground (run `/how` and `/why`), sketch (parallel candidate runners, often across
  different model families, each producing type signatures and a rationale), cross-judge with a
  different model against a rubric, implement against the sketch, scrap if the design proves wrong.
- **Against adversarial plan review.** They never review abstract plans adversarially because agents
  "start hallucinating theoretical risks"; open questions get answered by prototypes instead.
- **Planning playbook.** Each task is structured around proof; tests alone do not count as
  verification. Plans are validated by a script for structure. They commit big plans temporarily and
  deletes them when done.
- **In practice.** Four prompt examples, ending on Slack: `/poteto-mode do it` in a thread that
  already has the context.

research tools (`/how`, `/why`, `/recall`, `/teach`) research a *codebase*; they do not check a claim

worth installing for the writing pipeline. pstack's natural home is your engineering bots (the PR PM

loop is prose instructions, and the prose is exactly where it failed on 12 Sep. Two small

### Lever A: quote check

`quote_check.py <draft>` extracts every quoted string of six or more words, searches saved primaries,
and prints JSON per quote: **found in a primary**, **found only in a research note** (the exact path
by which the killed teach-a-task quote came back on 12 Sep), or **found nowhere** (composite suspect).
It needs one habit change: save any primary we intend to quote to `References/primary-sources/`
as `SOURCE_<slug>_<date>.md` when it is fetched. The convention exists and has been used twice; the
Sat 12 primaries were never saved there, which is why a composite could live in a research note
unchallenged. Honest limits: it proves a string existed in the snapshot, not that the page still says
it (the freshness re-sweep stays), and your own quoted speech needs an allowlist marker. **About 2 to
3 hours with pytest.**

### Lever B: window sweep and plan lint

`window_sweep.py <publish-date>` lists every piece in `Substack Published\`, `Substack Scheduled\`
and `Substack Drafts\` within seven days either side by publication date taken from the filename,
names the folder each is in, and prints each piece's `## ` headers and final two paragraphs plus a
count of header forms. With `--candidate "<text>"` it checks proposed replacement text against the
window before the panel applies it. `--plan` checks a week plan for exactly one `STATUS BOARD`, a
`TUESDAY GATE:` and a `SATURDAY GATE:` line. `--charter` diffs the installed editor-panel skill against
the `Writing Flow\` snapshot, which the panel already demands every run. This removes three failure
classes on record: the 12 Sep forward sweep that read a stale snapshot and reported Sun 13 as
missing (`feedback_file_verification.md`), the Rd3 seat misquoting the window file, and the 5 Sep
double board. It also saves tokens every panel round. **About 2 to 4 hours with pytest.**

Neither lever is built. Both would go on a branch under `heinlein/scripts/` or `Writing Flow/`, and
that is Lars's call.

## For Sat 19 (why the verdict is a planned piece)

Sat 19 is part two of the published Nine Bots piece, and stage 2 is a "here's how you build it" give
with portable prompts. These posts are a published example of exactly that genre, by the author of a
bot named in Part 1. Two uses, neither as a source:

1. **Keep each stage in one mode.** Stage 1 (what I built and why) is explanation; stage 2 should be a
   tutorial a newcomer can finish and see something work; the prompt addendum is dry reference. Tan's
   own first draft failed by mixing all four modes in one document, which is the risk in a piece
   carrying architecture, instructions and prompts at once.
2. **Independent corroboration of the design choice.** Tan's "Build the Lever" and "maintained as code"
   rules arrive at the same place as `heinlein/README.md`'s "scheduled tasks are stubs, behaviour lives
   in this folder." One line at most, with Tan's employer named in the same breath, because the plan
   already says Sat 19 is probably not the Grok Bot beat.

Tan's Slack example (a routine that tries to reproduce every report in a feedback channel) is a
possible stage-3 example outside writing, but your own Zendesk issue-patterns bot is closer and yours.
