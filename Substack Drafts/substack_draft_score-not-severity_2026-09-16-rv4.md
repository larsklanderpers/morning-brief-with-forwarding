On 1 September a vulnerability in OpenAI's Codex Desktop app entered the public record scored 9.8 out of 10, which is about as bad as the scale goes. OpenAI did not score it, and neither did the National Vulnerability Database.

That sentence is not particularly a complaint about either of them, but it is indicative of a pattern. The 9.8 ties the highest score ever attached to any Codex product in the NVD's records, and nothing else in the desktop app's history comes close. OpenAI described the bug precisely and shipped fixed builds for macOS, Windows and the Microsoft Store on the same day. The NVD, as I wrote on 3 September, told the world in April that it would no longer routinely supply a severity score for most of what comes through it, and this type of thing is *most of what comes through it.* Two weeks on, its record for the Codex bug still reads *Undergoing Analysis*. So the 9.8 came from the third place a score can live in a CVE record, and it is the place almost nobody reads: a container labeled ADP, filled in after the fact by a CISA enrichment program, with the field next to it set to `Exploitation: none`.

I want to talk today about that container, because since June it is no longer a footnote, and in a week that emphasizes labels with no one's name attached, the lovely abbreviations that describe it become non-load bearing despite all implications to the contrary. The same program that wrote the 9.8 now writes three of the four answers that decide how fast a US federal agency has to patch anything at all. And it wrote `no user interaction` on a bug whose own vendor says you have to open something for it to fire.

## The line across the top of the strip

If you have ever had an ECG (an electrocardiogram, the sticky-pads-on-the-chest test), you have seen the mechanism this piece is about, and you may not have noticed it. Along the top of the printout, above the actual trace, the machine prints its own interpretation in capitals. ABNORMAL ECG. POSSIBLE ANTERIOR INFARCT. CONSIDER ISCHEMIA. No signature, no initials, no name. An algorithm read the waveform and wrote a verdict on the record before any person looked at it.

Every cardiologist will tell you the same thing about that line: it is a prompt, not a diagnosis, and you read the trace. The machine over-calls constantly. It sees a fast heart rate and a slightly odd baseline and prints something that will frighten a patient half to death, and the trace underneath, read by a person, says *you ran up the stairs to the appointment*. The line at the top exists to make sure a busy clinic does not miss the one strip in a hundred that matters, which is a perfectly good reason for it to exist, for both the clinic's protection and the patient's.

The trouble starts in the clinics where the cardiologist is not there. There the line at the top is what the triage nurse acts on, because it is the only reading in the room, and the protocol on the wall was written on the assumption that somebody with the training would be along to read the trace before anything irreversible happened. When the somebody stops coming, the protocol does not change. It just starts running on the algorithm's capitals, which are only one part of the truth.

That is the vulnerability record in 2026. The trace is the vendor's description of the bug. The line across the top is the score. And as of April the person who used to read the trace for the long tail of vulnerabilities has, in writing, stopped. 

## Three containers, one number

A CVE record is not one document. It has compartments, and it matters which compartment a number is in.

The first belongs to the CNA, the CVE Numbering Authority, which for this bug is OpenAI itself. That container holds the vendor's own description and, if the vendor chooses, the vendor's own severity vector. OpenAI's description is specific: Codex Desktop *"automatically inspected Git metadata and working-tree status when a user opened a workspace. If the workspace contains a repository with preserved attacker-controlled `.git/config`, the `attr.tree` setting and a configured clean or process filter can cause Git to run an attacker-controlled program."* That is a real bug and a nasty one. Code runs with the user's privileges, outside the Codex sandbox, and credentials are in reach. It is nasty enough and risky enough that it is worth patching today if you have not already. OpenAI published no severity score for it at all. The first container, then, is empty of numbers.

The second belongs to the NVD, and for this bug it says *Undergoing Analysis* and nothing else, which after April is what most records will say for a long time, and for many of them for good. So, no numbers there, either.

The third is the one I want you to look at (which is mostly because it is the only one that exists). It is the ADP container, where that abbreviation does not refer to the payroll company, but rather for Authorized Data Publisher, and the publisher here is `CISA-ADP`, the output of a CISA program called Vulnrichment¹ that fills in what the CNA left out -- basically takes the original submission and adds meaningful data to it at an automated level, without human interaction. It is the only place in the whole record where a severity score appears. And what it wrote was `CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`, base score 9.8, CRITICAL.

Walk that vector against the human interpretation of each of those abbreviations in the sentence.

- `AV:N` is attack vector network.
- `PR:N` is no privileges required.
- `UI:N` is no user interaction.

Now go back to OpenAI's text: *when a user opened a workspace*. The bug fires when a person opens a prepared repository in the app. A vector that says no user interaction, written onto a description that says a user has to open something, is the ECG machine printing INFARCT above a trace of somebody who jogged in from the parking lot.

And the same container, in the same record, written by the same program, carries a second set of answers in a different format, called SSVC (a decision-tree scheme CISA uses instead of a score). The role recorded against those answers is *"CISA Coordinator"*, which is a desk, not a person; whether a script or somebody at that desk chose the values, the record does not say. They read `Exploitation: none`, `Automatable: yes`, `Technical Impact: total`. So one record, one author, says in one field that this is a maximum-severity network bug needing no click, and in the field beside it that no exploitation has been observed. It is not on CISA's exploited catalog either; I checked the catalog itself. Two structured negatives, sitting under a 9.8 that traveled into every brief that mentioned the bug.

The fair concession is that a score -- or at least that score -- is not supposed to encode whether anyone is exploiting a thing, only how bad it would be if they did. Granted. But `UI:N`, in particular, is not a judgment call about *likelihood*. It is, rather, *a factual claim* about the mechanism, and the vendor's own text contradicts it.

## What the same program said about the other one

On its own the Codex record could be a one-off. Sadly, it is not. And regardless of the troubling nature of the Codex record, there are other problems in this structure that are clear and present.

On 8 September, inside Microsoft's September release, Microsoft published CVE-2026-81381: *"Insufficiently protected credentials in GitHub Copilot and Visual Studio Code allows an unauthorized attacker to disclose information over a network."* Same shape of bug as the Codex one, if you squint: an AI coding assistant sitting inside the developer's editor, with the developer's credentials, and a way for something the developer opened to reach them. Microsoft is its own CNA and, unlike OpenAI, Microsoft supplied a vector: `UI:R`, user interaction required, base score 6.5, medium.

The same CISA program then enriched that record too. Its answers (translated for simplicity of review): `Exploitation: none`, `Automatable: no`, `Technical Impact: partial`.

Put the two side by side. Two assistants, one fortnight, both leaking something out of the editor through a thing the developer opened (that, feasibly, pretty much any developer has likely opened at some point). The one whose vendor supplied a vector got a cautious enrichment, automatable no, impact partial. The one whose vendor supplied no vector at all got the maximum on every field: network, no privileges, no interaction, automatable yes, impact total, 9.8. I do not know the program's decision rules and I am not going to guess at them. I can tell you what the two records say, and that a reader sorting a queue by score will put the 9.8 at the top and the 6.5 somewhere on page three, and that the two bugs are a great deal more alike than that ordering suggests.

The trust boundary in both cases is the same, and it is not the network. It is the repository you opened. That is the actual security finding in this pair, and it is not visible from either number. 

More to the point, the potential severity of these two items is not really adequately *represented* by those numbers -- arguably in either direction. The 9.8 may be high; the 6.5 is almost certainly low. For most IT organizations, running at full speed with a consistent lack of resources to sit there and read through the entire thing (which is a bit of a challenge, given Microsoft's Patch Tuesday has reached record levels of patches repeatedly this year, with over 900 patches, the most ever, this month alone), the items which get triaged are likely to be the 9s and higher, or even the 9.5s and higher -- and an item with nearly as much likelihood and systemic risk does not fall into either corpus, making it far less likely to be addressed.

So, as with so many things I spend my time thinking and writing about for us both: so what? Why does it matter if an overworked security group misses a problem that better proactive security likely would have caught in the first place anyway?

## Since June the answers have a deadline attached

Until this summer, all of the above would have been an argument about hygiene, held by a bunch of techies about just that -- something that no one else would have really cared about. A wrong vector in an enrichment container is embarrassing, it pollutes dashboards, and, honestly, it wastes our mutual Tuesday. What changed on 10 June is that the container *became an input to a legal obligation.*

On that day CISA issued Binding Operational Directive 26-04, *Prioritizing Security Updates Based on Risk*. A BOD is a compulsory direction to federal civilian agencies; they do not get to opt out. And this one does something its predecessors did not. It sets the remediation timeline for every vulnerability off four variables: *"Asset Exposure: Is the vulnerable asset publicly exposed? KEV Status: Is the vulnerability... on CISA's Known Exploited Vulnerabilities Catalog? Exploit Automation: Is an adversary able to automate all the steps necessary to exploit the vulnerability? Technical Impact: Does an adversary gain partial control or total control of the vulnerable asset after exploitation of the vulnerability?"*

Then, in the next sentence, it says where the answers come from: *"CISA publishes answers to KEV Status, Exploit Automation, and Technical Impact for every CVE ID through services such as the Vulnrichment Program."* The footnote under the remediation table repeats it. Those three elements *"are elements CISA provides to the CVE database through CISA's Vulnrichment Program for every vulnerability with a CVE ID."* And in the list of what CISA itself commits to do under the directive: *"Provide vulnerability metadata to the CVE database via the Authorized Data Publisher mechanism, such as currently provided by the Vulnrichment Program."*

Go back to the Codex record with that in mind. `Automatable: yes`. `Technical Impact: total`. Since June those two fields pick a row in a federal remediation table, and the program that wrote them is the program that wrote `UI:N` on a bug that needs a click. The directive is explicit that the timelines begin *"when either (1) CISA adds the vulnerability to the KEV Catalog, or (2)... the agency enumerates or identifies the vulnerability on an asset"* and updates its dashboard, *"whichever event occurs first."* So a federal desktop with a vulnerable Codex build on it, once it is enumerated, has a timeline, and the timeline was chosen by an enrichment step nobody signed, whose other answer on the same record the vendor's own text contradicts.

Three more things in the directive are worth having straight, because a lot of what circulates about federal patching is now simply out of date, and between the risk factors and the legal exposure, "out of date" is no longer just an inconvenience, it is a consequences-bearing problem.

The first is that CVSS is not in it. The timelines run on those four variables, in a system called SSVC, and the directive's only mention of the number everybody quotes is definitional: technical impact *"is similar to the Common Vulnerability Scoring System (CVSS) base score's concept of 'severity.'"* Similar to, which is not the same thing as used. So in the same year, the public score lost its human author at NIST in April and lost its seat in the federal timeline in June, and the field that replaced it in the timeline is written by the same enrichment program.

The second is that the directive *"supersedes and hereby revokes... BOD 22-01: Reducing the Significant Risk of Known Exploited Vulnerabilities."* Every sentence you have read this year that says a catalog listing means a fixed number of days under 22-01 has been wrong since 10 June. The catalog survives and is now more important, not less; the old directive behind it is gone, and the timelines are variable. The catalog entries themselves now carry a field that did not exist before: *"Forensic triage required per BOD-26-04,"* yes or no. For the two Windows zero-days from last Tuesday it reads No, with a due date of 22 September. For the shortest row, the directive's own note says the agency must remediate *"within the timeline (three days) and carry out a forensic triage of the asset to assess whether the system is compromised."* Days are calendar days. That is the whole of what I will say about the table, because the table itself is published as an image and you can read it yourself -- and you can determine the weight of the directives by context.

The third is the tone, and it is the opposite of what I expected. The vendors counting this month's release are attributing its size to AI-assisted discovery. The regulator writing the binding rule says, in its background section, that attackers' use of AI *"may further narrow the time defenders have to react."* May. Further. The most cautious sentence in this whole story was written by the body with the power to compel, and what it says it is for is prioritizing *"high-risk vulnerabilities for timely action, while deferring action against low-risk vulnerabilities."* Patch-everything is over, by directive, for the one set of organizations that could be ordered to do it. What replaces it is a table, and the table is fed by Vulnrichment.

If you are not a US federal agency this does not bind you, and the directive says so: *"Unless directed by the governing procurement contract, this Directive does not apply to contractors."* The next clause is the one to notice if you sell into that market: agencies *"must review all contracts to determine what modifications are necessary."* Expect the rider. Expect to be bound by contract. The biggest takeaway from this: expect yet another Ad Hoc Regulatory Regime to step into your day-to-day operations with not a whole lot of guidance.

## 970 patched, two exploited

As I noted briefly above, *all of this* landed in the biggest month there has ever been for the thing it governs.

Microsoft's September release, published on the 8th, fixed somewhere around 970 vulnerabilities. Qualys counts 974 and calls it *"Microsoft's largest security update ever"*; the Zero Day Initiative counts 972 from Microsoft proper and 997 with the external and Chromium items; Tenable counts 964. The spread is a scope question, not a disagreement, and I did the counting exercise for August two weeks ago and will not rerun it here, because I think it is a bit extraneous to the point. What is critical is both the *direction* of the count and the *velocity* of the increase: against Qualys's own figures for July (570) and August (about 400), September is roughly two and a half times the month before.

The number that did not move is the one that matters for the argument. Two vulnerabilities in the release were under active exploitation, and both are local privilege escalations rated 7.8 by Microsoft. Not critical, not remote, not a 10. Dustin Childs at ZDI counted twenty patches he would call wormable, and that is his count, not Microsoft's. And on the question of where the volume came from, ZDI and Tenable both point at AI-assisted vulnerability discovery, and Microsoft has said nothing at all. Childs's version: *"AI-assisted vulnerability discovery shows no signs of slowing down. However, we have not seen a correlating spike in active exploits - yet."* Tenable's Narang, quoted in SecurityWeek: AI discovery *"is creating larger haystacks, but it isn't finding more needles."* Hold onto that one as we look through the week -- we keep coming back to this same thing where the numerator and the denominator are both critical for understanding numbers and ratings, and this conversation is no exception.

Now look at where the highest scores in the month sat. The three top-rated items were a 10.0 in Azure AI Language, a 10.0 in Azure AD B2C and a 9.9 in Entra ID, and all three were fixed server-side by Microsoft before disclosure, with no customer action required. If you are in Australia and your team spent Wednesday chasing those, they were already closed before you read the advisory. Meanwhile the only two things anybody was actually exploiting were 7.8s that every administrator has to install *by hand*, that are already at risk *in the wild*, and that collectively pose, in my professional opinion, far more exposure to far more companies than the three top-rated items did.

The ranking and the work queue point in opposite directions. Nothing improper happened there; it is just what a score is. But it is also exactly the property that a process which sorts by score, and then has a deadline attached to the sort, cannot survive. The line across the top of the strip was never supposed to be the treatment plan.

## One vendor kept score on its own machine

One more table before the fixes, because it is the only place anyone has published the comparison the Codex and Copilot records only imply: a machine's severity call next to a person's, on the same bugs, in the vendor's own hand.

Anthropic runs a coordinated-disclosure program for open-source vulnerabilities its models find, and its public dashboard (counts as of 26 August) carries a table almost nobody has quoted. Of 1,017 findings that completed triage, the table sets Claude's initial severity rating against the rating external security firms gave after review. The headline is reassuring: 85.2 percent exact agreement, 97.1 percent within one band. The machine is not wildly wrong. But look at the direction of the misses. The model rated a bug higher than the humans 133 times and lower 18 times. And of the 137 findings the model called critical, 33 stayed critical after a person looked. The rest came down, most of them one band, thirteen of them all the way to low.

Anthropic's own explanation is the sentence I want you to carry: *"Project maintainers often apply project-specific severity rules that Claude does not have access to at run time, so what one maintainer rates as critical another may rate as low. The external security research firms incorporate that context, which is why their assessments tend to be lower."* The context that moves a critical down is the context that is not in the record. A firewall in front of the thing. A deployment that is internal-only. A person who has to open a repository before anything fires.

Two cautions before you weld this to the Codex record. This is a model estimating severity before triage, which is a different pipeline from CISA's enrichment, and Anthropic sells a security product on the back of it, so the dashboard is a vendor's ledger of its own work. Read it as that. But the direction it shows is the direction the ECG machine over-calls in, and it is the direction the Codex record went: where the first rating and the reviewed rating disagree about how bad a thing is, the first leans up, and the reason is the same every time. It cannot see past the record.

## Two fields and one column

The instinct after a piece like this is to distrust every score, and that is the wrong lesson (I think?). Maybe a tighter lesson is to distrust every number provided by a government? Regardless, the scores here are still the fastest sorting key you have if this is something in your responsibility set. The change is that for a growing share of them there is nobody you can ring about the number, and for the ones that matter to federal timelines the fields that count are now sitting in a container most tooling does not display. So the work is small and specific, and carries disproportionate impact.

**Sort this month's queue by who does the fixing before you sort it by score.** The three highest-rated items in September needed nothing from you (because they were fixed before disclosure). The two exploited ones needed *everything* from you, the whole way down to a manual patch deployment. A queue sorted by base score puts the closed 10.0s at the top and buries the 7.8s that are being used against people. One extra column, *fixed by vendor / fixed by us*, applied before anything else, would have made September's queue honest on the first morning. Do it for the release that is out now, and then leave the column in for the future and for your team to evaluate against as you return to the patching corpus.

**Take the single highest score in your open queue and hold its vector against the vendor's own sentence.** Not the whole queue. One record. Maybe two if you are feeling sassy. Open the CVE and find the vendor's description, then find the vector, and check whether they describe the same bug. `UI:N` against *"when a user opened"* is the giveaway in the Codex record, and `PR:N` against a description that says *authenticated* is the other common one. Where the vector and the vendor disagree, the vendor's sentence wins, and the sentence gets pasted into the ticket next to the vector so the next person to look at it can see why the priority moved. You will find *at least* one of these. When you do, you will have found the container the score lives in, and after that you will not be able to un-see it, no matter how many patches come out next month.

**Put the exploitation field beside the score in every ticket your scanner opens.** The Codex record carries `Exploitation: none` in the same container as the 9.8, and it is absent from the exploited catalog, and neither fact made it into a single headline about the bug. Both are structured fields; both are free; both fit in a ticket template. A 9.8 with `none` beside it and a 7.8 with a catalog due date beside it read very differently to a human with patch experience (as they should), and the whole point of this piece is that the human is now the only reader left for most of these, and your particular obligation as the human or the manager of the human is to make sure you read them *properly,* in a way different than any commonly-available automated process will read it.

None of that requires you to own anything new, hire anyone, or write a policy. It requires you to look at two fields that were always in the record, in a compartment that stayed shut while a public body was still doing the reading for you but which is now wide open and which *the obligation to read is now entirely yours.*

## The trace is right underneath

The CVE record for the Codex bug has an author field for its severity, the way every record does. The author is a program, in the only sense the record allows: a CISA initiative, a role name, and no person on the field. That is not a failure of the program; it did the job it was built for, which is to make sure a record does not sit empty in the month that the human layer went quiet. The failure is downstream, in every dashboard, brief and patch policy that took the capitals across the top of the strip as if a person had initialed them, and in a directive that now reads three of that program's answers as the basis for a compulsory deadline.

The machine will keep printing its verdict in capitals. It is not going to stop, and it should not. The trace is right underneath it, in the vendor's own words, and it has been there the whole time. The capitals will mislead you; your judgment is, as with so many things in the AI and cybersecurity spaces, the one thing that will save you. Exercise it. Repeatedly and wisely.

¹ Vulnrichment is CISA filling in missing information on other people's CVE records. When someone files a CVE, the vendor or researcher who files it (the "CNA") often leaves out the severity score, the type of weakness, and any sign of whether it matters. NIST's vulnerability database (NVD) used to add that detail to every record, but it fell far behind. So in May 2024 CISA started adding the missing context itself.
